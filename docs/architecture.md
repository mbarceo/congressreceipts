# Architecture

Congress Receipts (congressreceipts.org) is a **static website**: HTML, CSS, JavaScript and JSON files served as-is by GitHub Pages. There is no server, no database and no build step on the host. All the work happens on a contributor's computer: Python scripts download official records, turn them into JSON files, check them, and the results are committed to git. Merging to `main` publishes.

```
 official sources                    your computer                                   the web
┌──────────────────┐   fetch_*.py   ┌──────────────┐  build_*.py  ┌───────────┐  git   ┌──────────────┐
│ House Clerk XML  │ ─────────────▶ │ data/raw …   │ ───────────▶ │ data/*.json│ ─────▶ │ GitHub Pages │
│ senate.gov XML   │  (ignored by   │ (not in git) │              │ (in git)  │  PR →  │ congress-    │
│ FEC API          │   git)         └──────────────┘  verify_*.py └───────────┘  main  │ receipts.org │
│ congress.gov API │                                  checks the                       └──────────────┘
│ member press     │                                  JSON against                            ▲
│ pages, Census …  │                                  the raw data                            │
└──────────────────┘                                                     site/*.html + site.js render the JSON in the browser
```

## The two halves

| | What | Where | Who writes it |
|---|---|---|---|
| **Pipeline** (build time, Python) | Downloads raw records, computes figures, writes `data/*.json`, verifies every claim | `scripts/` | Developers |
| **Pages** (run time, browser) | Fetch the JSON and draw it. Static text uses `{{tokens}}` filled from the member's config | `site/`, `hub.js`, hub pages | Developers |

Nothing is computed in the browser except display work (sorting, filtering, charts). If a number is on a page, a script produced it and a checker re-derived it.

## Repository layout

```

members.json                    every tracked member (the registry the hub and publisher read)

scripts/                        ONE copy of every pipeline script, shared by all members
template/                       skeleton tracker.config.json + data/*.json for a new member
site/                           SOURCE of the member pages (index, money, stances, votes, ...), site.js, site.css
<state>/<member>/               one tracker, e.g. ca/padilla/, md/van-hollen/
    tracker.config.json           identity, FEC ids, peers, curated page text (committed, hand-edited)
    data/                         built JSON (committed) + curated inputs (committed) + raw downloads (NOT committed)
    assets/portrait.jpg           official portrait
    *.html, site.js, site.css     BUILD OUTPUT copied from site/ by publish.py (never edit)
index.html find.html attendance.html leaders.html backlog.html about.html     the hub pages (edited by hand)

```

A member's URL is its folder: `congressreceipts.org/ca/padilla/`.

## Key design decisions

1. **One copy of everything shared.** Pages live once in `site/`, scripts once in `scripts/`. A member folder holds only its config, its data and its portrait; the page files inside it are generated by `scripts/publish.py`. Fix a bug once, every member gets it.
2. **Everything member-specific is data, not code.** `site.js` reads `tracker.config.json` and fills `{{short}}`, `{{poss}}`, `{{chamberName}}` and so on, so the same HTML serves a House member and a senator (`data-only="house"` / `data-only="senate"` hide the parts that don't apply).
3. **Scripts take no member arguments.** `./tr ca/padilla build_votes` sets `TRACKER_DIR`, and `scripts/config.py` loads that folder's `tracker.config.json`. No script hardcodes a member, district or ID.
4. **Nothing is typed that a source can supply.** Votes, tallies, dollar figures and ranks come from official records through the scripts. Curated text uses placeholders (`{Vote}`, `{yea}`, `{nay}`) that the scripts fill from the roll call.
5. **Every claim is checked.** `scripts/run_checks.sh` extracts every sourced claim the pages show and verifies it against the source. A misquote, wrong vote or wrong tally fails the build. See [verification.md](verification.md).
6. **Raw data stays out of git.** Raw FEC files include donor names and street addresses, and raw roll-call XML is large and re-downloadable. They live under `data/raw/`, `data/fec/raw/` and similar folders, all in `.gitignore`. Only built JSON is committed, and donor names are never published (only employer, occupation and totals).
7. **Static and cache-safe.** Pages link `site.js?v=<hash>` and `hub.js?v=<hash>`; `publish.py` rewrites the hash whenever those files change, so a visitor never runs an old script against new data. `hub.js` also forces data files to revalidate (`cache: "no-cache"`).

## Runtime behavior

**Member pages** (`ca/padilla/stances.html` …)
1. The page loads `site.js` in `<head>`. `site.js` fetches `tracker.config.json` once and exposes `TRACKER.ready`, a promise of the display object `M` (names, pronouns, chamber, labels).
2. Once the DOM is parsed it replaces every `{{token}}`, hides chamber-specific blocks, fills the portrait, and adds the sticky tab bar.
3. The page's own script runs inside `TRACKER.ready.then(M => …)`, fetches the `data/*.json` files it needs, and renders them. A missing file shows a "not built yet" note.

**Hub pages** (home, Find your rep, Who's showing up, Leaders tracker, Backlog Queue, About)
- Plain HTML plus `hub.js`, which draws the header and footer (and a favicon if the page has none) and works on member pages too.
- Each reads hub data from the root `data/` folder (see [pipeline.md](pipeline.md#hub-data)).

Pages must be served over HTTP. Opening the `.html` files directly from disk breaks the `fetch` calls. Use `python3 -m http.server 8000`.

## Deployment

GitHub Pages serves the repository root from the `main` branch (legacy "deploy from a branch" mode, no workflow). There is no CI and no build on GitHub. Therefore:

- **Merging a pull request to `main` publishes it**, usually within a minute or two.
- Everything that should appear on the site, including generated pages and built JSON, must be committed.
- Nothing on `main` is checked automatically. Contributors run `./tr <member> run_checks` before opening a pull request.

The old per-member repositories (`ca-rep-29-tracker`, `ca-rep-45-tracker`, …) now hold only redirect pages that send visitors to the new URLs (`scripts/redirect_stub.py`).

## Members and formats

`members.json` lists each member with a `format`:
- `shared`: uses `site/` and `scripts/`. Every new member is `shared`.
- `legacy`: the older layout, where a member kept its own pages and scripts. No member uses it today; `./tr` still detects a member-local `scripts/` folder, and `publish.py` only adds the shared header to such members.

## What reads what (the dependency map)

```
members.json ──▶ publish.py            (which folders get pages)
             ──▶ build_attendance.py   (needs each member's votes.json AND raw roll-call XML)
             ──▶ build_leaders.py      (reads each member's committed data/ only)
             ──▶ build_directory.py    (matches tracked members into the Find-your-rep directory)
data/queue.json ─┐
data/congress.json ┴▶ backlog.html     (queue status per member, keyed by bioguide id)
```

Because `build_attendance.py` recounts missed votes from the official XML as a cross-check, **rebuilding the attendance page needs every tracked member's `data/raw/`** on your machine. Re-download with `fetch_votes` (see [how-to: rebuild the hub](howto/rebuild-the-hub.md)).

## Stack and requirements

- Python 3 (developed on 3.14), **standard library only**. No `pip install`.
- A POSIX shell with `zsh` for `./tr` and the key wrappers (macOS, Linux, or WSL on Windows).
- `git` and the GitHub CLI `gh` (optional, for pull requests).
- Free API keys: FEC and congress.gov (see [CONTRIBUTING.md](../CONTRIBUTING.md#api-keys)).
- Front end: hand-written HTML, CSS and vanilla JavaScript. No framework, no bundler, no npm.
